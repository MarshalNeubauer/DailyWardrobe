# CLAUDE.md

## Workflow

- **Merge automatically.** When a task is finished and tested, commit, push, open a pull request against `main`, and merge it without asking. Then tell the user what was merged and link the PR.
- **Don't merge when:**
  - tests fail or a change couldn't be verified;
  - the result is uncertain or only partly works;
  - the user says to wait.

  In those cases, push the branch, report the problem, and leave the PR unmerged.
- If the working branch's earlier PR is already merged, start the next change on top of the latest `main`. Merge `main` into the branch rather than force-pushing.
- The app is served from `main` by GitHub Pages, so a merge is a deploy.
- **Other sessions may be merging at the same time.** Right before merging, fetch `main`; if it moved since the branch was made or last updated:
  1. merge `origin/main` into the branch and resolve any conflicts;
  2. if `main` changed `CACHE` in `sw.js` or `PLAN_RULES` in planner.js, and this branch bumps it too, bump it again to one above `main`'s value (two sessions bumping to the same number is a single bump, so phones would miss the second change);
  3. re-run `npm test` on the merged result, push, and only then merge. If tests fail after the merge, apply the "Don't merge" rule.
- **The re-run after merging `main` is small.** It runs only the tests that both `main`'s incoming change and yours can affect, and says so ("main has moved since `npm test` last passed on this branch").
- When `main` brought only docs, or code that none of your tests uses, it prints "Nothing more needs to run" and stamps the map for the merged files: commit the map, push and merge.
- The re-run is your whole selection again, as before, when both sides changed the same file (a second `CACHE` bump in `sw.js` counts), when `main` changed `tests/run.js`, `tests/impact.js` or `package.json`, or when you edited a file after the merge.
- The small re-run needs `npm test` to have passed on the branch before `main` was merged in, with its map committed: so test and commit first, then fetch and merge `main`.
- Measured: a branch that selects 89 tests (100 s); `main` moved by a docs change: 0 run again (1 s); `main` changed `openStats()`: 6 run again (7 s).
- **No GitHub test run.** GitHub doesn't run the tests on pull requests (the user dropped it to save the wait). Your own `npm test` on the final branch is the only gate: merge right after it passes, without waiting on GitHub checks or subscribing to the PR.
- **`npm test` runs only the checks the change can affect** (the user's rule: never the whole suite for a small change). It compares the branch with `origin/main`, prints what changed and why each test runs, and runs nothing for a docs-only change.
- `npm run test:all` runs every check. It is not needed before a merge; use it only when the selection looks too small for what you changed.
- Test runs rewrite `tests/impact.map` (what each test uses). Commit it with the change: later sessions choose their tests from it.
- **The map must be in the commit (enforced).** `git push` is refused while `tests/impact.map` has uncommitted changes; commit it and push again. Never bypass it with `--no-verify`.
- **A changed app file needs a new `CACHE` name (enforced).** The service worker serves one version at a time, so phones take changed files only when `CACHE` in sw.js changes; `git push` is refused when a file in sw.js's `ASSETS` differs from `origin/main` while `CACHE` is still `origin/main`'s (`cacheStale` in tests/impact.js, part of the pre-push check): bump it to one above `main`'s, run `npm test`, commit and push again.
- If a change reaches `main` without its map, or without a passing `npm test` on the final files, the next session's `npm test` notices and runs every check. So run `npm test` after your last code edit, then commit everything it changed.
- A conflict in `tests/impact.map` needs no thought: `.gitattributes` merges it by keeping both sides' lines (`merge=union`).
- Never tell the user to download a backup file before a change: the worker keeps daily backups and Settings → Roll back undoes a bad change (see `sync.js`).
- **Run only what you need while working.** `node tests/run.js <name>` (or `TEST_ONLY=<name>`) runs just the `tests/*.test.js` files whose name contains `<name>`. Run `npm test` once before pushing, and once more only if `main` had to be merged in.
- **CLAUDE.md: one fact per line.** Add a new bullet under the file's heading instead of extending an existing one, so sessions working in parallel don't edit the same line and conflict.

- a reading takes about half the time it did: `binMedians` takes each fold step's median from typed arrays sorted numerically (comparator sorts of plain arrays were half the time), `labGrid` works out `rgbLab` inline with its sRGB curve from a table (`LAB_LIN`), the crossing-direction search builds each angle's projection once, `periodCh` runs on typed arrays; the numbers are the same: 94 readings (every fixture photo four ways, 10 seeded synthetic cloths) came out identical to before, and `tests/sett.test.js` went from 36 s to 17 s
- the full sett (`analyzeSett`/`settFromCanvas`): every band of one repeat in its own colour (per-step medians in Lab, merged until neighbours differ by ΔE 5; a 1–2 step band lying between its neighbours is their blurred edge), the direction, the lines crossing the other way (the residual after the main bands, projected; thread colour = 2 × pixel − band), and the scale (`cr`); stored as `item.sett` `{v:2,a,bands:[[hex,w]],cross:{d,bands:[[hex|null,w]],r},cr,tr,src}`
- `period()` takes the shortest whole fraction of a repeat that matches nearly as well (a clean pattern also matches at 2–3 repeats)
- `analyzeSett` finds the directions on a 320px copy and measures on a sharper one (up to 900px) so fine stripes keep their width; repeats are found in colour (`periodCh` over L*, a*, b*: a tattersall's red and green lines of one lightness stay apart); crossing lines are looked for after a moving average is taken out (`detrend`: light falloff and folds are not lines) and their repeat is at least 4% of the length (not the weave texture)
- directions are found from a colour-difference image (each pixel's Lab distance from the cloth's median, so a light-blue line on khaki linen counts even at the same lightness), with no coherence gate; `opt.straight` (every type but ties, from `settFrom`) tries only upright and level, ±6°; crossing lines are searched and marked in colour too (each step's kind is its strongest change: lighter/darker/bluer/…)
- the repeat is searched with and without the profile's slow drift and both candidates are scored on the drift-free profile (`corrAt`); without a plain repeat the drift-free one counts only above 0.75 (a plaid tie with no full repeat in view stays whole)
- the sharp copy is read in 8 strips running along the lines (`stripProfiles`): a draped cloth's lines wave, so one straight projection smears them; the repeat comes from all strips together and each strip is shifted into line (`stripShifts`, `foldBins`)
- sparse lines (windowpane, pinstripe) whose repeat doesn't match well (correlation under 0.6) are found one by one (`linePeaks`/`lineModel`: kept only where about half the strips have them, gaps varying under 25%), and every pixel is lined up on its strip's nearest line, so unevenly spaced panes (drape, a close-up taken at an angle) still fold into one repeat; the user's linen windowpane blazer (`tests/fixtures/blazer-windowpane*.jpg`) is the test case
- with a sharp photo and a close-up, the close-up's colours are shifted so its ground matches the photo's (the photo usually has a white wall to set exposure), and the swatch takes the close-up's scale (`cr`), since it sits beside it
- a narrow band (under 20% of the repeat, a pinstripe, a pinline) takes its strongest step's colour (if 5 ΔE or more from the ground) and its width at half contrast; each crossing line keeps its own thread colour (alike ones merged); the bands are measured without the pixels under the scarcer kind of crossing line (a gingham's white stays white)

### `sync.js`

- backup/sync through the worker's `/sync` endpoint (KV)
- backup file download/restore
- When nothing changed on the device since the last sync (`sync_mark`: the backup's version and a fingerprint of the wardrobe), it asks `GET /sync?v=<rev>:<saved>` and neither downloads nor uploads the backup
- any local change takes the full merge path
- (replaces the bullet above against a worker with the small sync) a change syncs without the backup (`syncLite`, 2026-11-13): `GET /sync?lite=1&since=<sync_mark's version>` (`&v=` too when nothing changed here, so an older worker still answers `same` or the whole backup, and the old way runs) brings only the records changed since, photos as references `dwph:<hash>`, every tombstone, and `idx` (the backup's stamp of every item, day and the settings); the device takes its own copy of a referenced photo (`phIn`, compared by hash with the same item's photos) or downloads it (`GET /sync?ph=<hash>,…`, `PH_BATCH` 40), merges as before, and `POST /sync {baseRev, baseSaved, day, reason?, delta, photos}` sends only records newer than `idx` and only photos whose hash the backup lacks (`phOut`)

- away: `item.away = {why:'laundry'|'cleaner', since, back|null}` is stored together with `item.paused` and `item.arrives = back`, the mechanism of a piece bought and on the way: `inRotation(i, n)`, `planSim`'s `byOn(n)`, the picker, "Suggest another" and the locked week need no code of their own, and the plan takes the piece back from the day after its date
- `careSend(id, why, back)` sends a piece away (not one already out of rotation) and releases the upcoming days pinned to it (`careRelease`, as `togglePause` does); its toast has Undo (`careUnsend`, which doesn't count as cleaned); `careSetBack(id, date)` sets or clears the date
- coming back sets `item.cleaned` (YYYY-MM-DD) and deletes `away`, `paused`, `arrives`: by itself in `checkArrivals()` (app.js) the day after `away.back`, with `cleaned` = that date on every device, or with "It's back" (`careBack`), cleaned today
- wears since cleaning: `careCounts()` counts, per item, the days of `wornDays()` (stats.js) dated after `item.cleaned`; kept on the plan cache (`cache.careW`), so anything that resets `cache={}` recounts
- a wear on the day of `item.cleaned` itself is not counted (the piece was cleaned after it); so a piece marked back in the morning and worn that same day loses that one wear
- limits: `careLimit(type)` = `settings.care[type]`, else `CARE_DEF` (suit 5, blazer 6, pants 4, shirt 1), else 0 = never; `careState(i)` → `{wears, limit, each, due, near, over}`: due at the limit, near one wear short (limits of 3 and more)
- a limit of 1 (shirts) means washed after every wear (`each`): such pieces are never flagged one by one (every worn shirt would carry a tag); the Care page shows them as one line per type with "All washed today" (`careCleanedType`)
- "Cleaned today" / "Washed today" (`careCleaned`) sets `item.cleaned` without sending the piece away, with Undo
- the item sheet's Care card (`careCard(i)`, `#ivcare`, appended to the Rotation card's markup in `itemBody` so the sheet's last line is untouched): the count ("Worn 4 times since cleaning (Nov 3) · due after 5"), "Send to the dry cleaner" / "In the laundry" (the laundry first for shirts and socks, `careWashed`), and while away: since when, an optional "Back on" date and "It's back"; only for `CARE_ABLE` types, not for a piece on the way

- the Wardrobe grid: `careTag(i)` ("At the cleaner's · back Nov 20" / "In the laundry") in the `.pausetag`, and `careBadge(i)`, a quiet `.caretag` "Due for cleaning" on a due piece
- the page (`#care`, `openCare`, `renderCare`, `careLists()`; in Settings as "Laundry & cleaning" under Wardrobe stats): Due for cleaning (most overdue first), Nearly due, Washed after every wear, Away now; each row has "Send to the cleaner" and "Cleaned today", away rows "It's back"

- Today: `careNote(o)` adds one quiet line (`#carenote`) under the cards, on today only, when today's suit, blazer or odd trousers reaches its limit with this wear or is past it; nothing otherwise
- Settings → Care (`#sc-care`, `renderCareUI` from `renderSettingsExtras`; `'care'` is in `SET_CATS` in app.js, after weather): a dropdown per type in `CARE_TYPES` (`setCareLimit`: Never, After every wear, After 2–10 wears) and "A worn shirt waits" (`setLaundryDays`, which releases the coming week's locks like `setDarkShirts`); the summary `#sum-care` is written by `renderCareUI`

### `safety.js`

- data safety (loaded right after app.js, before tagging.js and sync.js): failed saves, storage that can't be opened, keeping the wardrobe, kept tagging copies, tagging failures, unsaved Add cards, a device's first sync; `tests/safety.test.js`, `tests/safetysync.test.js`
- `storeFailure(e)`: an error is a storage failure when `txs`/`atomic` marked it (`e.dwStore` = 'read' or 'write'), it is a `QuotaExceededError`, or it is an IndexedDB request's error event
- `saveFailed(e)` toasts it in plain words (`storeFailText`: "Couldn’t save: your phone’s storage is full…", else the browser's reason), once per 1.5 s since one failed save rejects more than one promise (`put` chains a `.then`)
- the `unhandledrejection` listener shows storage failures nobody caught and leaves every other rejection alone; Add's `save()` has no try/catch of its own, its rejection arrives there and the card stays to be saved again
- `dbDown`/`dbErr` are set by safety.js's own `db.then` at load: it is queued before sync.js's `db.then`, so the listener already knows storage is down when that one rejects, and stays quiet
- `storageDown(e)` (from the start-up chain's `catch`, through `afterScripts`): when `db` didn't open (or a start-up read failed) it puts `#nostore` over the whole page ("Your wardrobe can’t be opened here … can’t be loaded or saved", the browser's reason, Try again = reload) and makes `header`, `main` and `nav` inert; other start-up errors still fall back to the empty Today as before
- `askPersist()`: `navigator.storage.persist()` once (`localStorage.persist_asked`, the answer in `persist_ok`), from `save()` after an Add card is stored, and from `safetyStart()` for a wardrobe that already has items
- `safetyStart()` runs at the end of the start-up chain (after `appReady`): `pruneTagImgs()` and the persist request
- `pruneTagImgs()`: removes from Cache Storage `dw-keep-tagimg` the sharp copies whose item is not in `items` (nor an Add card); at start-up only, since a deleted item can be undone for a few seconds; never with an empty wardrobe (a lost one comes back from the backup)
- tagging failures: `ask()` (app.js) calls `tagFailText(status, json, error)` for a refused answer or a thrown error; it returns the Add page's note (`aiError`) and keeps the plain reason in `tagWhy`; a 429 `{error:'limit', message}` shows the server's `message` as is
- `addFiles` calls `tagFailed(q)` when `ask()` gave nothing and a server is set: `q.tagErr`, drawn by `tagFailNote(q,i)` at the top of the card (`.tagfail`: "This photo wasn’t tagged." + the reason + Try again); `retryTag(i)` asks again and fills the card; the card can still be filled in by hand and saved
- `guardUnsaved()` (from `addFiles` and `addManual`, once: `guardOn`) installs the `beforeunload` listener: leaving asks first while `queue` holds a card that is not a failed read
- `adoptBackupSettings(local, data)` (called by `syncOnce` before the merge): on a device that has never finished a sync (no `localStorage.last_sync`) whose stored settings carry a newer stamp than the backup's, the backup's settings win key by key (`{...local, ...backup}`, the backup's stamp), are stored and applied at once; keys only the device has (`setupDone`) stay; why: first-run setup stamps its settings before the device is connected, and they replaced the backup's holidays, days off, own colours and learned preferences
- after its first finished sync a device's changes count by stamp like any other's

### `sw.js`

- service worker: one version at a time (see the bullets below; it used to fetch every app file fresh on each load)
- Add new app files to `ASSETS` and bump `CACHE`
- service worker: one version at a time. Installing downloads every file in `ASSETS` afresh (`cache:'reload'`) into the version's own cache (`CACHE`), and the page is then served from that cache only (cache-first; a file not in it comes from the network and is kept); works offline
- why: the earlier handler was network-first with a 4 s race per file, so an app reopened on a slow connection right after a release ran some new files and some old ones from the cache
- a new version installs in the background and waits (no `skipWaiting` at install): it takes over when the app is next started, or when the page sends `{type:'skipWaiting'}` (about.js `updateNow`); `{type:'version'}` with a message port answers the worker's version number
- a request made with `cache:'no-store'` is not handled (about.js reads the newest `sw.js` that way); `sw.js` itself is in `ASSETS`, so the page can read its own version from the cache
- `tests/sw.test.js` serves releases from its own server: a reload stays on the installed version, a bumped `sw.js` prompts and waits, Update switches and reloads with every file new, a version left waiting runs after the app is closed and opened, and a worker following the earlier network-first one takes over without a reload

- daily caps, testers only (`DEFAULT_CAPS` `{tag:40, pattern:10, photo:12, item:20}` per UTC day, `utcDay`; an invitation's own `caps` override them, `cleanCaps`): tag = `POST /` and `/tag-many`, pattern = `/pattern`, photo = outfit photos (direct, queued, `replace`), item = item pictures and one-piece edits (`photoCap`: a body with `swap`)
- over a cap: 429 `{error:'limit', what, cap, used, message, detail}`, the message a plain sentence ("Today’s limit of 12 outfit photos is used up. It starts again at midnight UTC.", `CAP_WORDS`); `detail` repeats it because the app's tagging errors show `detail`
- `spend(env, who, what)` counts before the AI call and answers null or `{status, body}`; `unspend` gives the count back when the call fails; a queued job remembers `cap` and `capDay` and `refundJob` gives it back when the consumer gives up, when `/render-queue` gives up on it, or when the photo was already there
- the counting is in the tester's `RenderHub` (`POST /use {what, n, cap, day}` → `{ok, used}`, kept in the object's storage as `use` = `{day, n:{…}}`; `GET /used?day=`): no KV write per AI call, since the free plan allows 1,000 KV writes and 1,000 lists a day for everyone together; without the `RENDER_HUB` binding `useCount` falls back to KV `use:<id>:<day>` with a 3-day TTL
- two more caps the app does not show protect KV's daily writes (`EXTRA_CAPS`): 60 photo uploads (`PUT /render`) and 20 feedback messages a day per tester
- a tester cannot choose `model`, `quality` or `complexity`: `handleRender` deletes them from the body before anything reads it, so a queued job keeps none either
- invitations, owner only (`handleInvites`): `POST /invites {name, caps?}` → `{id, code, name}`, the code 32 URL-safe characters from 24 random bytes, shown once, only its hash stored; `GET /invites` → `{invites:[{id, name, caps, created, off, used}], day}`; `DELETE /invites?id=` switches one off (`MAX_INVITES` 30 active)
- switching off: the tester's hub is told first (`POST /off`), so capped calls stop at once (`spend` answers 403); the `invite:` record is rewritten with `off:true`, which every other route sees as soon as KV shows it (up to a minute in another location)
- `GET /me` → `{id, name, role, caps, used, day}` (`handleMe`, `usedOf`; the owner: `caps` null and `used` all 0, the owner is not counted)
- `POST /feedback {text, version, where}` → `{ok:true}` (text 1–4,000 characters); `GET /feedback` (owner) → `{items:[{t, name, text, version, where}]}` newest first; one document `feedback:log`, messages older than 180 days dropped on every write and read, 500 at most, the key itself expiring 180 days after the last message
- `DELETE /account {confirm:'delete'}` → `{ok:true}` deletes only the caller's: a tester's `u:<id>:*` keys, their `invite:` record and line in `invites:index` (the code stops working), their feedback and their hub's storage; the owner's own families only (`OWNER_FAMILIES`: the backup, `snap:`, `render:`, `job:`, `jobfail:`, `jobrun:`), never `u:*`, `invite:*`, `invites:index` or `feedback:log`
- a Worker may make about 50 KV calls a request on the free plan, so `wipeSome(env, ns, budget)` deletes a part (30 calls in the request) and the queue finishes the rest a part per message (`{wipe:'owner'|'u:<id>:', n}`, `runWipe`); without the queue the answer carries `more:true` and the same call deletes the next part
- lists replaced by reads: `kvMeta(env, key)` reads a key's metadata with `getWithMetadata(key, {type:'stream'})` and never reads the value, so `syncVersion` (every sync) and `keepSnapshots` (every save) no longer list KV; a KV without `getWithMetadata` (the test mocks) lists as before; a queued photo's earlier `jobfail:` is deleted only when it is there (`dropFail`: a delete of nothing still counts as a write)
- `POST /` reads at most 15 MB of body and stops there (`TAG_LIMIT`, `readCapped`) → 413
- `/fetch` refuses anything but a public host (`publicHost`: no IP address in any spelling, no `localhost`, no single-label or `.local` / `.internal` / `.lan` / `.home` / `.corp` name), follows redirects by hand (5 at most) checking each stop, checks the page's share image the same way, and stops reading at its caps (15 MB photo, 600 kB page)
- `ALLOWED_ORIGIN` may be several origins separated by commas: the matching one is echoed in `Access-Control-Allow-Origin` (with `Vary: Origin`), any other origin gets 403
- KV budget with testers, for the record: a queued photo is about 6 KV writes (job, jobrun twice, the photo, two deletes), so a tester using every cap is about 200 writes a day; five such testers reach the free plan's 1,000; moving the job records into the Durable Object would be the next step
- not done here: `GET /render?list=1` is still one KV list per app start per person (a read cannot replace it without an index document that costs a write per photo)
- `tests/accounts.test.js`: the owner and two testers against one mocked KV, queue and a Durable Object per name: isolation of sync, snapshots, photos, lists, queue and push; the owner's exact key names; caps (429, clear the next day by moving `Date.now`, refunds, KV fallback); invitations, revoking, `/me`, feedback, account deletion; the hardening; and the app (invitation link, Connection page, limit messages)
- existing tests that still pass unchanged show the owner's path is as it was (`queue`, `todayqueue`, `sync`, `snapshots`, `render`, `render-sync`, `prefetch`, `paste`, `tagging`, `multi`)

**Planner rules:** whenever a change alters how outfits are chosen (planner.js scoring, groups, rotation), bump `PLAN_RULES` in planner.js. On the next start the app clears swaps and vest choices on every day after today (`checkPlanRules()` / `replanFuture()` in app.js; formal days, today and past days stay), so the new rules apply to the whole future. Settings has "Re-plan upcoming days" for the same on demand.

Colours always come from the item's tagged colours, matched by brightness rank, never from the photo, except an item's `sett`: it is read from the white-balanced sharp photo or close-up at the user's request, so its bands keep their measured colours. Pattern lists in `PATS_BY` (core.js) must stay in sync with the prompt in `worker.js`, and so must the per-type colour lists (`COLS_BY` / `DIAL_COLS` in core.js = `TYPE_COLORS` / `DIAL_COLS` in worker.js; `tests/colouraudit.test.js` checks it). Each item type offers only colours it really comes in; an off-list tag moves to the closest allowed colour (`fitCol`), and a colour an existing item already has stays selectable for it.

## Testing

`npm run test:all` (or `node tests/run.js`) serves the repo, drives it in headless Chromium and checks rendering, swipe/layout on phone and iPhone Duo viewports, the planner against an independent rule checklist, belts/leather/metals, the outfit score, photo-less adding, pattern detection, and `worker.js` with mocked bindings. Add a check for every behaviour you change; extra suites can go in `tests/*.test.js`.

- After a tap, tests wait with `settle(page, ms)` (passed to every test file) instead of a fixed `waitForTimeout`: it returns once no animation runs and the scroll is still, waiting up to 2×`ms` (`DEBUG_SETTLE=1` logs each wait)
- `tests/run.js` gives every `tests/*.test.js` file one shared Chromium (a file's `chromium.launch()`/`close()` open and close only its own contexts) and prints the slowest files at the end.
- tests run several at a time: `tests/run.js` starts worker processes (`node tests/run.js --worker`; `together`, `worker`), one fewer than the processor cores, at most 8; `TEST_JOBS=<n>` sets the number, and `TEST_JOBS=1` runs them one after another in one process, printing as it goes
- each worker process has its own local server, Chromium, recorder and Node coverage (`bench`) and runs one test at a time, so two tests never share any of them; the built-in suites of `run.js` are handed out like the files
- a test's lines are kept in its worker and printed together when it finishes (`• name`, then its checks); the parent adds up the counts and what each test used, and writes `tests/impact.map` once at the end
- the slowest tests start first, by the times of the last run (`node_modules/.cache/dw-test-times.json`, never committed)
- a worker process that dies fails the test it was running, and another takes its place

- a class inside `:not(…)` no longer makes a rule "for a new class" (`.card:not(.fresh)` styles the old cards); `selNeeds` reads only what an element must have, outside brackets

### Writing a change the selector can narrow

- New behaviour goes inside a function that is called from where it is used, not in a block that runs when the script loads: `shopSwipe()` is called from `openShop()`, so only tests that open the sheet run it.
- A listener is installed by such a function the first time it is needed (a flag like `shopSwipeOn` keeps it to once), not by a top-level `(()=>{…})()` or `document.addEventListener(…)`.
- A new top-level `const`/`let` is fine: it is followed by name to the functions that use it.
- A new constant gets its own `const` line, never appended to an existing `const A=1,B=2;`: the selector takes one statement as one change, so every name on that line counts as changed.
- Measured in assemble.js: `,ASM_XX=1` appended to the `const ASM_VER=2,ASM_DE=14,…;` line selected 90 of 92 (`ASM_VER` is named by `asmKey()`, which runs at start-up in every test); `const ASM_XX=1;` on its own line selected 2.
- The `ASM_*` numbers in assemble.js are one `const` per line for that reason; keep them so.
- Don't add the call to a function that every test runs (`show()`, `renderToday()`, `closeShop()`): an edit there selects everything; call it from the narrowest function that needs it.
- A new visual element gets its own class name (`.shop-grab`), not a new selector built from existing classes or a `::before` on an existing element: a rule for a class the app never had selects no existing test.
- State for an existing element also gets a new class (`.x.new-state`) rather than new declarations in its base rule: a rule that applies on every page (`#shop-sheet`, `body`, `.card`) selects every page test when its declarations change, and rightly so.
- Check before running: `node tests/run.js --changed --list` says what changed and which tests it selects; "top-level code" or "the stylesheet as a whole" in that line means the change can be restructured.
- Measured on the swipe-down change (handler and grabber): as a load-time block with `.shop-top-head::before` it selected 89 of 91; as `shopSwipe()` from `openShop()` with `.shop-grab` it selects 5 (`shop`, `shopswipe`, the start-up suite, and two tests that read `shop.js` as text).
- The slide-away part of that change edits the rules of `#shop-sheet` and `#shop-backdrop`, which are on every page: it selects 89 of 91 however it is written.
- Other measurements: an edit inside the item sheet's `touchmove` listener selected 89 of 91 and now 5; a new `.ivhead::after` rule selected 89 and now 17.
- The suite runs on Windows too (the owner's PC, `C:\code\DailyWardrobe`, 16 cores: 2169 checks in 42 s, 8 at a time); `.gitattributes` checks every text file out with LF (`* text=auto eol=lf`), since Git for Windows defaults to `core.autocrlf=true` and CRLF broke source checks that look for `\n`
- a test that makes its own git repo turns `core.autocrlf` off in it (`impact.test.js`): that repo has no `.gitattributes`, and a merge there wrote CRLF on Windows
