# CLAUDE.md

## Workflow

- **Merge automatically.** When a task is finished and tested, commit, push, open a pull request against `main`, and merge it without asking. Then tell the user what was merged and link the PR.
- **Don't merge when:**
  - tests fail or a change couldn't be verified;
  - the result is uncertain or only partly works;
  - the user says to wait.

  In those cases, push the branch, report the problem, and leave the PR unmerged.
- If the working branch's earlier PR is already merged, start the next change on top of the latest `main`. Merge `main` into the branch rather than force-pushing.
- The app is served from `main` by GitHub Pages, so a merge is a deploy.

## Project

Static app served from `main` by GitHub Pages (no build step). Classic scripts loaded in order, sharing one global scope:

| File | Contents |
|---|---|
| `index.html` | markup and script tags |
| `styles.css` | styles |
| `core.js` | colours, types, item helpers (no DOM; also loaded by background workers). `isWorkday(d)` = a weekday in `settings.workdays` that is not a day off (`offName(d)`: a public holiday in `settings.holidays` `{country, list:[{d,n}], skip}` that is not skipped, or one of the user's own `settings.daysOff` `[{d,n}]`; dates as `YYYY-MM-DD`, `isoKey`). The planner skips days off like weekends |
| `planner.js` | outfit rules, `outfit()` / `buildPlan()`, `rateOutfit()` (no DOM). Jackets rotate by rest and avoid the previous workdays' colour group (`jacketGroup`, `colourRepeat`), and so do shirts and ties (`shirtRepeat`, `tieRepeat`; white and light blue shirts only mildly; dark shirts count as one look and black/charcoal/grey/silver ties as one, `shirtLook`/`tieLook`); the same jacket colour group with the same shirt look and tie look as either of the last two workdays is a whole-look repeat (`lookRepeat`); each jacket remembers its last two outfits so its tie and shirt colour vary (`comboRepeat`); a jacket pinned to one of the next 3 workdays is held back before its day, the next fixed day's colour is avoided, and the suit before a blazer day avoids the colour of the blazer that is due (`fixedAhead`); odd trousers rotate on a long rest (`ptRest`, up to 60 days, since blazer days are weekly) and shoes avoid yesterday's pair when another suits; steel blue is a mid-tone shirt, not a `darkShirt` (cutoff 95); every month from two months back is simulated from one shared start so months agree; the simulation is resumable (`planSim(start).upTo(day)`; `buildPlan(y,m)` runs one from `planStart`), and a day with no jacket of its kind (a blazer day with no blazers) takes the other kind |
| `detect.js` | stripe/check detection from photos (canvas) |
| `figure.js` | Today's torso figure, redrawn at the user's request: no head or neck (cropped at the collar, like the original handoff), athletic build, shirt collar band with points on the tie knot, slim notched lapels around a wide opening so the vest shows, set-in sleeves cut by the shoulder line (`clipShoulder`), the left forearm across the chest with the watch, the right hand at the button. No tap targets on it. Fabrics come in as ready-made `<pattern>`s from `figFabric()` in draw.js; keep the pattern ids (`suitB/suitL/suitR/shirt/tie`), `bladeP`, `.fig-clip`, `.fig-watch`, `.fig-vest` and no `<use>` inside `<clipPath>` |
| `draw.js` | procedural fabric patterns (`fabricDef`), `figureSvg()` glue for the torso figure, accessories, wardrobe thumbnails |
| `analysis.js` | "what to buy" analysis (no DOM; runs in `analysis-worker.js`, a Web Worker) |
| `app.js` | IndexedDB storage (items, day history, settings; generated photos in `meta` as `render:<combination key>`), forms (the Wardrobe editor can replace, rotate, zoom-crop and undo an item's photo without touching its tags: `photoTools`, `setPhoto`), screens (Today: the swap card under the score, the pieces list folded into `#ibox` (each piece unfolds into its photo, `toggleRow`) and the month plan into `#mbox`, both unfolding in place; `goToday()` from the date-bar pill and the Today tab; `planMonth(y,m)` / `planFor()` keep one shared `planSim` in `cache` (anything that changes the wardrobe, history, settings or weather must reset `cache={}`); `newDayCheck()` moves on to today when the app is reopened on a later day; Wardrobe (an opened item takes the full width of its row from where it was, so the tapped box stays put; its row-mates slide under it and a blank `.gi-gap` keeps later rows; tapping the open photo/swatch, Close or Done folds it back; `openItem`/`closeItem`/`flipWardrobe`, FLIP animations), Add), product pictures for shoes/belts/socks/pants/coats/watches (`itemDesc()`; made from the item's own photo by image edit when it has one, saved as `render:c<16 hex>` of the description; Settings button generates the missing ones), batch photo generation, background download of the worker's photos for the month on screen and the next, nearest day first (`prefetchRenders`, after one `GET /render?list=1`), swipe gestures, days off in Settings (`setHolidayCountry`, `toggleHoliday`, `addDayOff`, `renderDaysOffUI`; the holiday list is refetched monthly, `refreshHolidays`), weather (16-day forecast; beyond it `loadClimate()` fills `climate` in core.js with the location's usual monthly highs from Open-Meteo's archive, kept in `localStorage.wx_norm`, so `dayClimate()` does not fall back to a temperate calendar) |
| `sync.js` | backup/sync through the worker's `/sync` endpoint (KV), backup file download/restore. When nothing changed on the device since the last sync (`sync_mark`: the backup's version and a fingerprint of the wardrobe), it asks `GET /sync?v=<rev>:<saved>` and neither downloads nor uploads the backup; any local change takes the full merge path |
| `sw.js` | service worker: network-first app files, offline fallback. Add new app files to `ASSETS` and bump `CACHE` |
| `worker.js` | Cloudflare Worker: photo tagging via the Claude API (secret `ANTHROPIC_API_KEY`, optional `CLAUDE_MODEL`; falls back to Workers AI binding `AI`), `/sync` (KV binding `WARDROBE`, requires `APP_TOKEN`; the backup's `{rev, saved}` is kept as the KV key's metadata so `?v=` and the PUT conflict check don't load the backup) `/fetch` (downloads photo links for the app, requires `APP_TOKEN`), `/holidays?country=XX` (public holidays from Google's public holiday calendars, for countries Nager.Date lacks; the app asks Nager.Date itself first; requires `APP_TOKEN`), `/tag-many` (several items in one photo: Claude lists every item with a confidence and a rough box in thousandths; the app crops each into its own Add card) and `/render` (POST with `mode:'item'`: a product picture of one item from a text description via OpenAI image generation, stored under the given key; otherwise POST: realistic outfit photo via OpenAI's image edit API, secret `OPENAI_API_KEY`, optional `OPENAI_IMAGE_MODEL` (default `gpt-image-2`), `OPENAI_IMAGE_QUALITY` (an outfit request or queued job may set its own `quality`: low/medium/high); photos are saved per outfit combination (`comboKey()` in app.js: the shirt by base colour only, the jacket/tie/clip/watch by how they look, plus the vest) as `render:c<16 hex>` in KV (no expiry) and in `meta`, so a combination is never generated twice and GET/PUT `/render?key=` share it between devices (`GET /render?list=1` lists every kept key); older `render:<date>` copies are migrated on first use; requires `APP_TOKEN`; POST `{mode:'queue'}` keeps an outfit's inputs as `job:<key>` in KV and sends `{key}` to the Cloudflare Queue `wardrobe-renders` (binding `RENDER_QUEUE`), whose consumer (`queue()` export) makes the photo in the background, retrying temporary OpenAI errors and recording others as `jobfail:<key>`; GET `/render-queue` lists pending and failed jobs; the Settings month batch uses this and falls back to generating on the page when the worker has no queue); deployed automatically by `.github/workflows/deploy-worker.yml` (Wrangler, config in `wrangler.toml`; it creates the queue if missing, so the token needs Queues edit) when a merge to `main` changes it, once the repo has the `CLOUDFLARE_API_TOKEN` secret and `CLOUDFLARE_ACCOUNT_ID` / `WARDROBE_KV_ID` variables; until then the workflow skips and the user deploys by hand |

**Planner rules:** whenever a change alters how outfits are chosen (planner.js scoring, groups, rotation), bump `PLAN_RULES` in planner.js. On the next start the app clears swaps and vest choices on every day after today (`checkPlanRules()` / `replanFuture()` in app.js; formal days, today and past days stay), so the new rules apply to the whole future. Settings has "Re-plan upcoming days" for the same on demand.

Colours always come from the item's tagged colours, matched by brightness rank, never from the photo. Pattern lists in `PATS_BY` (core.js) must stay in sync with the prompt in `worker.js`, and so must the per-type colour lists (`COLS_BY` / `DIAL_COLS` in core.js = `TYPE_COLORS` / `DIAL_COLS` in worker.js; `tests/colouraudit.test.js` checks it). Each item type offers only colours it really comes in; an off-list tag moves to the closest allowed colour (`fitCol`), and a colour an existing item already has stays selectable for it.

## Testing

`npm test` (or `node tests/run.js`) serves the repo, drives it in headless Chromium and checks rendering, swipe/layout on phone and iPhone Duo viewports, the planner against an independent rule checklist, belts/leather/metals, the outfit score, photo-less adding, pattern detection, and `worker.js` with mocked bindings. GitHub Actions runs it on every PR (`.github/workflows/test.yml`). Add a check for every behaviour you change; extra suites can go in `tests/*.test.js`.

The user's phone may run the Dark Reader extension. The page opts out via the `darkreader-lock` meta tag; keep it.
